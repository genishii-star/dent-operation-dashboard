Review Automation / Design

レビュー依頼の抑制

レビューパイプラインを完全自動化（オーナー承認の撤廃）するにあたり、「レビュー依頼を送りたくないゲスト」をDent側で持つための設計。判断はDentにしか無く、Airhostからフラグとして取得できない。

設計のみ / 未実装 2026-07-16 正本: DESIGN_review_exclusions.md

01 — Problem

なぜ投稿してはいけないゲストがいるのか

ホストがゲスト評価を投稿すると、Airbnbがゲストに通知を出してリスティングへのレビューを促す。トラブルのあったゲストを突けば、悪いレビューを自ら呼び込むことになる。

ゲスト評価を投稿
review_of_guest
→
Airbnbがゲストに通知
「ホストがあなたを評価しました」
→
ゲストがレビューを書く
リスティングに公開
→
良いゲスト → 得
トラブルゲスト → 損

前提の検証が要る。Airbnbのレビュー公開仕様（双方投稿 or 14日で公開、ホスト投稿が通知トリガーになる）は実挙動を確認していない。この図はその仕様を前提にしている。また「レビュー依頼 = review_of_guest の投稿」という解釈自体、別経路（Airhostメッセージ等）を指すなら設計をやり直す。

02 — Prerequisite

先に直すべき: 識別子の結合が名前頼み

抑制リストの鍵は確認コード。しかし今その確認コードはゲスト名のあいまい一致で引いている。この土台のまま抑制を載せると、取り違えが致命傷になる。

同名衝突で別人を掴む。最後の条件は「レビュー側の名前が、テーブル側氏名の第1トークンを含む」という緩さ。さらに .find() なので先に見つかった行が勝つ。

これを鍵に抑制判定すると、除外したゲストに投稿し、無関係のゲストを除外するという最悪の取り違えになる。

03 — Mechanism

抑制の仕組み

CSビューからフラグを受け、生成前と投稿直前の二重で判定する。承認を撤廃する以上、投稿直前のゲートが最後の砦になる。

パイプラインとゲート

CSビュー
対応した人が立てる
→
照合して弾く
未知のコードは 400
→
D1 review_exclusions
confirmation_code が鍵
Airbnb スクレイプ
週次
→
Gate 1 生成前
ドラフトを作らない
→
D1 review_drafts
Claudeで生成
→
Gate 2 投稿直前
最後の砦
→
Airbnbへ投稿
取り消し不可

なぜ二重か。状態が途中で変わるから。生成後・投稿前にクレームが入るケースを Gate 1 は捕まえられない。Gate 1 はドラフト自体を存在させない（＝誤投稿される文面が無い、トークンも節約）ための最適化で、安全性を担保するのは Gate 2。

fail-closed。review_of_guest で confirmation_code が null なら投稿しない（保留＋通知）。

損失が非対称だから。レビュー1件の取り逃しは軽微だが、悪いレビューは公開されると恒久的に残る。身元を特定できない予約について「抑制リストに載っていないこと」を証明できない以上、投稿してはいけない。§02の確定結合を入れれば null はほぼ出ない。

テーブル

CREATE TABLE review_exclusions (
  confirmation_code TEXT PRIMARY KEY,  -- HM...
  scope       TEXT NOT NULL
              DEFAULT 'review_of_guest',
  reason      TEXT,
  created_by  TEXT NOT NULL,
  source      TEXT NOT NULL,  -- cs-view | dashboard
  created_at  TEXT NOT NULL,
  released_at TEXT,          -- 物理削除しない
  released_by TEXT
);

返信は抑制しない。reply は既に公開されたレビューへの応答で、ゲストを新たに突く効果がない。抑制すべきは「まだレビューを書いていないゲストを起こす」review_of_guest だけ。全接触を断ちたい例外用に scope='all' を残す。

なぜ reservations に列を足さないか

Airhost
毎朝
→
d1SyncDaily
INSERT OR REPLACE
→
D1 reservations
洗い替え

列を足すと毎朝消える。d1SyncDaily がAirhostから予約を洗い替えるため。

別テーブルなら同期と独立に生きる。予約データは「Airhostのミラー」、抑制フラグは「Dent固有の判断」。ライフサイクルが違うものを混ぜない。

鍵の選定

候補可否

HM...		 ✓ Airhost チャンネル予約ID と一致 / CSが画面で見られる / 他OTAにも同概念があり将来拡張できる

04 — Contract

CSビュー連携 — 照合しないと機能しない

Dent側は受け口の契約だけ決め、上流の実装には踏み込まない。ただし1点だけ譲れない要件がある。

POST /internal/review-exclusions
  { confirmation_code, scope?, reason?, created_by }
  → 201 { ok: true }
  → 400 { error: "unknown confirmation_code" }   ← 譲れない

DELETE /internal/review-exclusions/:code   -- 解除 (released_at を打つ)
GET    /internal/review-exclusions        -- 一覧

書き込み時に D1 reservations と照合し、存在しなければ 400 で落とす。成功扱いにしてはいけない。

抑制リストは承認撤廃後の唯一のゲートであり、キーが1文字ずれれば黙って無効になる。「フラグを立てたつもりで、実は誰も守られていない」はフラグ立て忘れより悪い — CSは対処済みだと信じてしまうから。

これは机上の懸念ではない。既存のCSツール cs-form.html では 予約番号が手入力のフリーテキスト（cs-form.html:195）で、予約マスタとの照合が一切ない。同じ設計を持ち込むと確実に踏む。

立て忘れは設計で消えない。CSがフラグを立てなければ漏れる。ここは仕組みで完全には潰せない。緩和策は「遅延投稿（3状態モデル）」で既定を hold にすること（忘れても被害が減る）だが、§01の仕様検証が前提。

05 — Gap

承認撤廃で開くもう一つの穴

抑制リストが解くのは「誰に送らないか」だけ。「何を公開するか」は誰も見なくなる。この2つは別のリスクで、別の draft_type に効く。

review_of_guest
掲載先: ゲストのプロフィール
文面は定型の称賛で事故りにくい。真のリスクは投稿が nudge を起こすこと。
全自動 — 抑制リスト＋fail-closed が担当
reply (高評価)
掲載先: 自社リスティング
定型の礼状。公開されても事故りにくい。件数は多い。
全自動でよい
reply (低評価)
掲載先: 自社リスティング
クレームへの的外れな返信が、将来のゲストが読む場所に恒久的に残る。件数は少ない。
人を残す

抑制リストは reply の文面リスクを一切カバーしない。そして承認キューの元々の名前は「★低評価返信 — 承認待ちキュー」で、まさに低評価への返信を人が見るための仕組みだった。それを外すなら代わりの防御が要る。

ただし現状これは実装できない。scrapeUnrepliedReviews() が返すのは {review_id, guest_name, date, property_name, original_text} だけで、★評価を捨てている（airbnb-helpers.mjs:155-161）。カードのDOMには Overall quality / Rating N があり、本文開始位置の判定に数字行を使っているのに拾っていない。リスク階層化には rating の取得が前提。

06 — Rollout

段階導入

段階0は抑制リストと無関係に今すぐ入れるべき。名前一致の取り違えリスクは、抑制の有無に関わらず今そこにある。

  1. 確定結合への修正 ＋ 締切を Expires soon 準拠に
    依存なし。単独で価値がある。抑制リストの土台でもある
  2. review_exclusions テーブル ＋ Worker API（照合付き）＋ Gate 2
    依存: 段階0
  3. CSビュー連携 ＋ ダッシュボードに抑制状態を表示
    依存: 段階1
  4. Gate 1（生成前スキップ）＋ 抑制件数の通知
    依存: 段階1。抑制は黙って効かせない — 全件抑制されているのに「順調」と誤認する事故を防ぐ
  5. rating 取得 → reply のリスク階層化
    依存なし（並行可）
  6. 承認撤廃
    依存: 段階1〜4が安定してから
